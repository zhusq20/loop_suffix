# Loop投机解码墙钟测速：WFD与后缀树+浅层同引擎比较（2026-10-31，已完成，结果见[报告](report.md)）

用户2026-10-31指出，[上一批墙钟测速](../loop-suffix-spec-wallclock-20261031/protocol.md)里WFD用的是它自己的引擎，与我们的方法比较不公平，要求把WFD放进同一引擎测。随后用户决定：已有各臂（ar、shallow、suffix、both、both-path）沿用上一批的数字，只重测WFD。本批只做推理，不训练。

## 1. 问题

上一批得到“后缀树+浅层相对WFD：Ouro 0.93倍、Huginn 1.07倍”。但两边的引擎开销不同：WFD自带的逐词解码比我们的逐词解码快（Ouro 1.75倍、Huginn 1.52倍），所以这个比值把算法差异和引擎差异混在了一起。本批让WFD的调度在上一批各臂所用的引擎里运行，回答：**在相同引擎下，后缀树+浅层比WFD快多少。**

## 2. WFD在本引擎中的实现

WFD（arXiv 2609.23033，提交`4345209`的`generate_wavefront_dynamic`，贪心、不开KV共享、不提前退出）与“只用浅层”是同一个流水线：每个位置到深度d时用浅层第1候选起草下一个位置，到深度T时核对；核对出错就提交改正的词，冲掉后面所有在算的位置，改正的词从深度0重开。差别只有两处：

| 差别 | 只用浅层（上批） | WFD |
| --- | --- | --- |
| 草稿上限 | 每步最多起草K=16个词，到上限后这一步结束，从深度0重开 | 无上限 |
| Huginn的浅层读出 | 草稿的coda用单独的浅层coda缓存，读祖先的深度d coda状态，与离线teacher forcing一致 | 草稿与核对共用一个coda缓存：在算的祖先存的是深度d的coda状态，已提交的位置存的是全深度的coda状态 |

本批的`wavefront`臂：只用浅层、`max_draft`不设上限；Huginn用`shared_coda=True`，让浅层读出走全深度coda的缓存槽，节点的coda K/V在深度d写入、到深度T被覆盖，与WFD的读写顺序相同。Ouro没有coda，两种设置相同。

## 3. 引擎：与上一批相同，只为WFD加一个选项

代码以上一批的引擎为底，只增加两个默认关闭的选项（`shared_coda`、`flush_every`）。选项关闭时，其他臂的代码路径与上一批相同：fp32核对中AR每次调用48.09 ms，与上一批完全相同。

**为什么需要`flush_every`**：引擎在一步结束时才把已提交的节点写进主KV缓存，树内注意力读这一步的全部节点。各臂有K=16的上限，一步只有十几个节点；WFD没有上限，接受连续时一步会长到上千个节点，每次调用的开销随之增长，这对WFD不公平。

**做法**：前沿之上已完成的链节点累积到16个时，把它们写入主缓存，树内注意力从前沿开始读。前沿之上的节点已走满T步，剩下的节点都是前沿的后代，编号也更大，所以这样做与原计算等价。这样WFD的树缓冲区保持在与K=16一步相当的大小，读法也与其他臂相同（一段连续的节点）。

**已撤回的版本（19:15–19:46 UTC，已停止）**：先做过另一版引擎，每接受一个词就写入主缓存、只读祖先节点，并用它把所有臂重测。前4题显示，这版引擎让带草稿树的臂每次调用慢了2–5%，AR不变。用户随后决定不重测已有各臂，该批停止，已完成的部分（Huginn 5题、Ouro 1题）保留在`<root>/loop-wfd-same-engine-20261031/sb-chat/`，不用于结论。

## 4. 等价性校验

**CPU单元测试（28项，全部通过）**：
- 微型随机Ouro和Huginn上，`wavefront`臂（`flush_every=4`）与WFD原代码的输出逐词相同、R调用数相同：Ouro d=1、d=2两种，Huginn T=6、d=2（shared coda）。
- `flush_every`取1、3、16时，输出和调用数都不变。
- 带已写入主缓存节点时，树注意力与稠密参照一致。
- 无上限的链中，未被草稿命中的词数等于浅层草稿出错的个数。

**GPU fp32核对（真实权重，通过）**：每类1题、64个新词。`wavefront`的输出与AR逐词一致；与WFD原代码相比，6/6题输出相同、R调用数相同（Ouro 417 = 417，Huginn 3208 = 3208）。
