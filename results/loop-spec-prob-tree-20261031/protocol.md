# Loop投机解码：按猜对概率把候选放进草稿树的方法验证（2026-10-31）

用户2026-10-31要求先验证[计划页“方法”一节](../../docs/design/loop-spec-schedule-comparison-20261101.html)提出的放候选规则，不跑其他基线实验。本批只做CPU回放、GPU微基准和墙钟测速，不训练、不改模型。GPU步骤由用户确认卡和核之后再启动。

## 1. 要验证的方法

现行解码器（[loop-suffix-spec](../loop-suffix-spec-20261030/protocol.md)的`both`／`both-path`）把后缀树草稿和浅层第1名补位放进树，每步最多16层。计划提出的改法：

1. 浅层读出取前m名，猜对概率p超过阈值τ的都放入，不只第1名。
2. 后缀树续写、补位、兄弟候选都用同一个规则：按p和同一个τ决定放不放。
3. 去掉每步16层的上限，改为存活行数上限B，超出时删掉p最低的分支。
4. 可选：节点跑到更深一层（Ouro深度2、Huginn深度8）时，再读一次，按同一规则放入。
5. 核对规则不变，每个提交的词都是全深度贪心输出。

**修订（2026-10-31，S2中途）。** 以下两点原协议没有写明，按修订后的规则重跑全部扫描，旧结果保留：

- **接受即写入后缀树。** 每接受一个词就写入后缀树，并从新接受的节点重新起草。原实现只在一步结束时写入，去掉K上限后一步可持续数百个词，后缀树看不到这些词。缺陷由选择集上的逐题分析发现，见[报告§5](report.md#7-修订记录)。
- **读出时重新打分。** 节点到达读出深度时，已在树中的子节点按该深度的名次与概率重新计算p。这一步原协议没有写，现作为开关保留，并做了关掉它的消融。

p取从根到候选每条边猜对概率的乘积，每条边的概率由离线校准得到。计划由两个观察推出：放入一个候选，猜对时省T−r次块调用，猜错时最多白跑T−r行·次，所以当且仅当p/(1−p) > c_row/t_call时放入，阈值与放入深度r、loop深度T都无关。

**第二次修订（2026-10-31 22:00，v3，按用户采纳的建议）。** 用户转来的建议第4条要求从计划中采纳两点提高精度。按消融结果（报告§5）冻结为v3-C：

- 后缀树候选的边概率改用解码器内校准表：在选择集上回放v2，记录每个由路径上节点提出的后缀树候选是否猜对，按（条件概率、匹配长度、是否已有兄弟、距已提交位置几层）分档。
- 更深读出与深度d的读出联合打分（按两个深度的名次与更深读出的概率分档），重新打分后p≤τ即剪掉该分支。
- 建议中“更深读出不扩枝”作为消融D检验，数据显示它在两项指标上都被C支配，未采纳。
- 两个工作点：低负载τ=0.01，有负载τ=0.1（用户建议第3条）。

用户2026-10-31提醒：增加草稿数量会降低吞吐。单请求下多一行几乎免费，多请求时并不是，所以每个设置都要同时报延迟（每词调用数）与算力（每词行数、白跑比例）。

计划给出的放弃条件：出错点上第2–m名的覆盖率低于15%，就不放兄弟候选。更深读出带来的额外收益低于3%，就不采用。

## 4. 步骤

### S1 校准与覆盖率（CPU）

**边的猜对概率。** 在选择集的贪心路径上统计：
- 浅层候选：按（读出深度、名次1–8、读出概率分档、是否也是后缀树候选）统计等于全深度输出的频率。后缀树提出但不在前8名的，单列一格。
- 后缀树候选：父节点正确时，按（后缀树条件概率分档、匹配长度分档）统计猜对的频率。条件概率取ArcticInference给出的路径概率除以父节点的路径概率。
- 样本少于50的格子并入上一级分组。在确认集上画可靠性图，报告校准误差。

**覆盖率（P1）。** 用现行解码器回放，在每步因正确词不在树中而结束的位置，统计正确词在浅层深度d、更深深度读出前m名（m=2、4、8）中的比例。

### S2 回放扫描（CPU）

新写一个按块调用逐次推进的回放器，规则见第1节。每次调用先处理核对（删掉错的子节点），再处理读出（放入新候选、重算已有子节点的p），最后检查行数上限。

**计数的精确程度。**
- 块调用数在贪心路径上精确。
- 行数：错枝何时被删按其在路径上的祖先核对的时刻精确计算。错枝下的读出没有存，用同一位置贪心路径上的读出代替，行数因此是近似值，以墙钟批次实测为准。
- 每次调用记录存活行数与读出行数，之后可以套用任何耗时曲线。

**正确性检查。** 回放器设一个“现行模式”（第1名总是补位、后缀树`min_token_prob=0.1`、K=16），它的块调用数必须与前批`replay_request`逐题相同。单元测试另覆盖：只有一个候选时退化为逐词，τ=0且不设上限时调用数不多于现行模式，B删掉正确候选时调用数相应增加。

**扫描。**
- 逐项加改动，看收益来自哪里：现行 → 统一规则只用第1名 → 加兄弟候选（m=8）→ 去掉K上限 → 加更深读出。
- τ∈{0.3, 0.1, 0.03, 0.01, 0.003, 0.001}。
- B∈{不设, 256, 128, 64, 32}，在τ的较优值附近扫。
- P4的检验：对r=0（后缀树）、r=d、更深读出分别设阈值，看比单一τ能否再改善1%以上。

**选择。** 每个设置报每词调用数与每词行数，画出随τ、B变化的权衡曲线。在选择集上冻结两个工作点：
- 延迟优先：用S3的单请求耗时曲线把（调用数、每次调用的行数）换算成预计解码时间，取最小者。
- 吞吐不降：每词行数不超过`both-path`的引擎实测值，在此前提下每词调用数最少。

S3完成前的选择标为暂定。

**放入时的校准（补充）。** 在回放中记录每次放入时的p与该节点是否在贪心路径上，检查离线校准在解码器里是否成立（`loop_prob_tree_replay.py trace`）。

### S3 引擎微基准（GPU）

用户确认空闲的卡都可用。S3a在GPU 6、7，S3b在GPU 8、9，CPU绑在NUMA 1上互不重叠的核。

**S3b 多请求（用户建议第2条）。** 同样的总行数，比较三种排法：全部来自一个请求、每请求8行、每请求1行。每个请求有自己的前缀KV（256、1024、3584），同一请求的各行共用一次前缀读取。只计一次块调用的模型计算（Ouro整个层栈，Huginn adapter加core块），注意力为按请求分组的FlashAttention varlen，不含树掩码。脚本`scripts/loop_prob_tree_multireq.py`。

### S3a 单请求

在墙钟批次的引擎（`loop_tree_decode.py`）里，固定已提交前缀长度（256、1024、2048），测单次块调用耗时随存活行数1、2、4、…、4096以及读出行数的变化。行数测到单次调用耗时随行数线性增长为止，模拟多个请求共用一次调用、算力用满的情形。两个模型各测，Ouro在GPU 6（CPU 24–31），Huginn在GPU 7（CPU 32–39）。得到每行成本c_row、单次调用耗时t_call和开始变贵的行数。读出的成本分成两项分别测：一次调用里有没有读出，以及读出多少行。
