# Huginn eager 完整结果及论文主表建议

日期：2026-11-05。数据来自 `results/loopfill-eager-b1-b16-huginn-20261105`。29组完成、1组OOM，每组480题，共核对13,920条成功请求。本文仅重新提取与汇总已有产物，没有新增推理、计时或调参。

## 测量口径

Huginn-3.5B，T=32，BF16；六类Spec-Bench各80题；B=1/2/4/8/16表示continuous batching最大并发槽数，不代表整个过程始终满batch。每题最多1024个新token，128-token chunked prefill、packed attention、CUDA Graph与执行行填充均关闭。每个单元用一张NVIDIA L20X，八张卡分发独立单元，不是八卡联合吞吐。

每配置固定题序seed=0、单次计时。计时含prefill、decode、CPU调度及后缀操作，排除模型加载和预热。预热使用2B个请求、最多32新token；预热输出不进入正式历史。后缀历史为冷启动、请求完成后发布。融合配置N=16、Q=4、top-2、读出深度4/8；raw为固定c=1，online初值0.7、η=0.1、范围[0.25,2]。所有方法共用引擎，但WFD/LoopSpec保留各自调度与预算规则，不能称六方法都受N=16约束。

γ=32×Σstats.tokens/Σstats.calls，排除prefill首token；按逐请求loop steps计算，包含未提交token的推进。整体γ为比值的汇总，不是六类γ或逐题γ的算术平均。γ衡量串行循环节省，不是普通每次验证接受token数，也不是墙钟加速或总FLOPs。

## 结果支持的结论

- LoopFill-raw对AR吞吐比为2.24–4.19×，对同引擎LoopSpec为1.13–1.26×；online分别为2.34–4.20×、1.19–1.32×。这些是本协议中的观测比值，不是等输出无损加速或跨引擎SOTA结论。
- 两种融合变体在所有五档已完成测量中均超过WFD/LoopSpec/Suffix-only的对应成功点。WFD B16为OOM，无可比较吞吐。
- raw的γ为6.01–6.28，online为6.36–6.43，LoopSpec约4.84–4.91，Suffix-only约1.67–1.75。串行步骤节省与实际吞吐收益方向一致，但不同方法轨迹和输出不同，不能直接当成同轨迹因果分解。
- 六类任务中，B8 online的γ最高的是RAG 8.35，最低的是Translation 3.02；该异质性值得用机制分析解释，不宜只展示全体平均。

## 论文主表方案

建议主表标题为“同一eager执行引擎下的吞吐与循环效率”，两个模型分别一个panel；行保留AR、WFD、LoopSpec、Suffix-only、LoopFill-raw、LoopFill-online。列按B=1/2/4/8/16分组，每个单元报告token/s与γ。双栏版面可用上下两行单元格；若空间不足，正文保留B1/B4/B16，其余两档放完整附录，不只挑最优batch。Ouro未补齐前只给Huginn panel，不填估算或协议不同的历史值。

主表突出融合方法的收益，online作为附加改进。caption说明单次测量、生成长度可能不同、eager/Graph-off、同引擎基线和OOM。单次结果只加粗观测最大值，不写显著优于，不把空标准差填成0。另用六类任务γ表或图解释收益分布；无需为已有γ重新运行模型。

附件提供可直接纳入论文的Huginn LaTeX表。LaTeX表的缩写Suffix-only仅指本仓库实现，不应改成“官方SuffixDecoding”；LoopSpec/WFD也不是官方引擎性能复现。Graph-on历史结果必须另表、注明协议，不能逐单元择优混入当前主表。

## 还应补哪些数据（建议，不启动实验）

### 优先补齐核心证据

1. **Ouro-2.6B的同协议六方法主实验。** 先核对旧产物是否满足当前eager、输入、历史、参数与计时协议，只补缺项。理想补齐五档30单元；预算紧张可先三档B1/B4/B16的18单元，并同步收缩两模型主表列范围。不得用旧Graph-on数据直接填当前列。
2. **读出与接续预算消融（2026-11-09修订）。** 固定N16、根部Q4，比较“仅首次/两次浅层读出 × Top-1/2/4”六组（孩子Q4），再补两种读出下的Top-2/孩子Q8，共8个唯一配置。原四组来源开关消融已删除，不转移到附录补跑。统计γ、loop steps/token、rows/token和丢弃计算；不要求全量稳定墙钟测速。
3. **节点预算与权重消融。** 沿用N=8/16/32/64，以及固定c=0.5/0.7/1与online c0=0.7。与读出/接续预算面板复用后，每模型/B共14个核心唯一配置；用一行四个雷达图面板展示，详见[当前计划第4节](loopfill-paper-experiments.md#4-四维消融一行四个雷达图面板)。先审计旧日志，协议匹配的已有配置扣除。重点是固定c=0.7对照，否则不能证明online反馈本身的价值。
4. **机制trace。** 在相同已验证前缀和相同可见历史下测两来源的交集/独有命中、条件补救率；在保留的读出/Q配置的真实执行轨迹上测来源切换和节点成为根时已完成的循环数。离线覆盖不能替代真实接受收益。现有调用/行数计数可直接提取，缺失的路径归因和提前计算字段才需小规模分层trace实验。

### 无需新推理就能补进附录

逐类别γ、全部batch的输出量/耗时、请求时延p50/p95、TTFT、显存峰值、loop steps/token与rows/token、输出一致性；本次已导出full-metrics.csv。时延从槽位接纳开始，不含外部排队，不能作为有到达率负载下的服务SLO。峰值显存为框架allocated口径，不能等同于全设备总占用。OOM只描述当前实现/分配/硬件配置的失败，不是算法理论容量结论。

### 取决于论文主张的额外证据

当前规划明确暂不安排正确性诊断、质量评分、官方原生基线或重复计时；本次不恢复这些已撤销任务。但若正文要声称“保持质量/无损”或“online稳定提升几个百分点”，需要相应新增证据：

- 无损/质量不降：先核对完整输出分歧，再对相关任务做适用的质量评测，必要时做更长FP32与逐步状态检查。现有短检查和算法接受规则不能证明长BF16输出等价；一致率本身也不是任务质量分数。
- Online稳定提升：只对关键配置做有限独立计时与预先固定的请求顺序变化，报告运行级不确定性。请求级bootstrap不能制造GPU计时重复；不建议自动恢复整套三次重复矩阵。固定题序重复测运行噪声，改变题序还会改变完成后共享历史，两者应分开。
- 泛化/独立确认：480题已参与选参，应冻结参数，在未参与选参的新题集上做有限确认。现在再切分同一已见480题不能追溯地变成独立测试集。
- 若强调长上下文、历史适应或服务容量，再按需补上下文长度、冷/热历史和到达率曲线；不将它们扩成默认必做矩阵。
