# 纯后缀与融合方法的共用后端诊断（2026-11-04）

**后续进展（2026-11-05）**：已实现执行填充与验证形状预热，并完成Huginn B8/B16的480题验证，见[基线修复报告](loopfill-suffix-baseline-fix.md)。本文保留修复前的诊断数据；其中“尚未实现端到端提速”描述的是11月4日当时的状态。

本轮固定 Q=4、N=16、top2、孩子查询上限 (4,4)，不放宽草稿约束，不修改线上权重规则，不重跑正式 batch 矩阵。只新增 CPU profile、Graph 形状统计、固定输出缓存回放和相同输入的算子微测。生产解码器与正式结果均未修改。

## 结论与证据范围

当前主要优化方向是共用的模型验证后端，而非重写 Suffix Tree 检索。纯后缀推进次数更多、每次处理行数更少，更容易受调度和小算子开销影响；融合方法也承担这些开销，但利用更多并行节点摊薄了成本。

没有发现可据此认定“后缀算法写错”的证据，也没有完成对正式全量运行的 GPU 关键路径归因。CUDA Graph 调用命中率不是 GPU 时间占比，CPU profile 的累计时间包含等待和嵌套调用，不能相加当成独立耗时。

| 后缀查询 / 秒 | 1.568 | 6.317 |

纯后缀总计算行数更少，却有更多小批量推进。融合方法的速度优势不能仅用“计算行数少”解释。全 B1–16 中，查询耗时占比为：纯后缀约 0.04%–0.24%，raw/online 约 0.59%–1.41%。优化查询函数本身的直接收益有限；改变候选质量可能另有收益。

## 后端热点

[诊断入口](../scripts/loop_backend_diagnose.py) 保留正式 480 题 seed=0 的题序和前 16 题预热，预热输出上限 32；仅执行前 32 题、每题最多 64 新 token 的诊断流。Q、N 不变。产物位于 [formal-warmup-b8](../results/loopfill-suffix-diagnostic-20261104/formal-warmup-b8/DIAGNOSTIC.json)，CPU profiling 会扰动速度，不用于替换正式吞吐。

| 诊断项 | 纯后缀 | raw |
|---|---:|---:|
| 计时段不同 Graph 形状 | 124 | 498 |
| 已捕获图数 | 24 | 24 |
| Graph 调用命中率 | 32.39% | 23.41% |
| 假设事后选中最常见 24 种形状的覆盖上限 | 64.31% | 27.23% |
| 元数据 upload 调用 | 20,385 | 14,423 |
| upload 累计 CPU 时间 / 秒 | 2.600 | 1.030 |
| Tensor.tolist 调用 | 963 | 10,764 |
| Tensor.tolist 累计 CPU 时间 / 秒 | 0.672 | 0.873 |

短流的 Graph 命中率与全量结果不同，不外推短流比例。事后覆盖上限只描述该流，不能作为可用于测试集选图的策略。

具体实现原因：

- [Graph key](../src/llm_memory_editability/loop_optimized_decode.py) 包含操作、精确真实行数 R、分组数 G、查询宽度 Q、树宽度 N。这里的 Q/N 是执行张量维度，不等于算法参数 Q=4/N=16。真实行数变化会产生新图。
- 预热只保留至多 24 个常见形状；计时期不捕获新图。当前策略按调用次数选择，未按实际可节省时间选择。
- 每次推进重新构造 NumPy 元数据、上传三个张量、收集 hidden/static、回写结果。这些操作在 Graph 外。
- [LoopKV.upload](../src/llm_memory_editability/loop_tree_decode.py) 使用每种 dtype 两个 pinned 缓冲区并等待上次上传事件。该等待保障正确性，不能直接删除；可研究复用元数据和减少上传次数。
- readout 对各请求分别重排和提取 GPU 结果；浅层 top-m 有多次 `.tolist()`。融合方法也会受到影响。

独立的真实 Huginn recurrent 算子检查使用相同静态输入、关闭梯度，分别执行 eager 和已捕获 Graph，每种 20 次，三种形状输出逐元素完全一致。raw 的单次耗时分别为 **4.62→3.08 ms、5.04→4.47 ms、5.16→4.56 ms**。这证明已检查的共用计算路径存在 Graph 优化收益；微测排除了元数据准备、输入复制和调度，不能换算成整套解码的加速倍数。见 [有效算子检查](../results/loopfill-suffix-diagnostic-20261104/kernel-check-raw-b8-no-grad/budget-raw-b8-kernels.json)。最初未关闭 eager 梯度的检查已在其 DIAGNOSTIC.json 中明确作废，不用于结论。

纯后缀另检查了三种较小形状，逐元素输出也全部一致，耗时分别为 **4.53→1.83 ms、4.56→2.00 ms、4.38→1.76 ms**。该局部检查支持“小批量推进更受调用开销影响”的判断，仍不构成正式全量吞吐收益。见 [纯后缀算子检查](../results/loopfill-suffix-diagnostic-20261104/kernel-check-suffix-b8-no-grad/budget-suffix-b8-kernels.json)。

## 历史缓存：有小幅候选质量收益，尚不是主要瓶颈

当前 `CompletionSuffixCache` 的本请求 prompt 和已确认输出实时可见；只有跨请求共享输出推迟到完成时。并非“生成过程中整个 suffix cache 都不更新”。

对照本地固定版本 ArcticInference aca5d9a：其 `add_active_response` 同时更新本地树和全局响应树，因此其它请求可以立刻检索已确认输出。改成该策略不会增加草稿上限，但会改变候选、频率统计和并发完成顺序对结果的影响，不能作为完全不改变算法行为的工程优化悄悄替换。

[缓存回放脚本](../scripts/loop_suffix_cache_diagnose.py) 使用现有 B8 纯后缀的 480 条完整输出；固定 B=8，每个活跃请求轮流加入一个已确认 token，完成后补位。未来 token 只在检索完成后评分，不插入缓存。该调度是合成的，不能复现真实 GPU 调度或预测端到端吞吐。

| 53,769 个同前缀查询，Q=4 | 完成后共享 | 官方实时共享 |
|---|---:|---:|
| 第一个草稿 token 正确的查询比例 | 52.54% | 54.26% |
| 平均匹配草稿路径长度（不含 bonus） | 1.5005 | 1.5466 |
| 查询累计 CPU 时间 / 秒 | 1.148 | 1.461 |

51,926 次匹配长度不变（96.57%），1,459 次变好，384 次变差。平均匹配长度增加 3.07%，不等于运行速度增加 3.07%。实时共享的全局树内容更多，本次查询时间反而增加；单次顺序执行的 CPU 时间也不用于宣称稳定速度差。

当前包装层每次调用两个官方 cache，各查询本地树和全局树，因此实际做四次 native 检索，其中本地 cache 的全局树、history cache 的本请求树为空。结束请求时，history cache 还会把完整输出插入一个随即销毁的本地树。存在精简空间，但应避免为了省这点时间绑定官方私有字段。详见 [回放数据](../results/loopfill-suffix-diagnostic-20261104/cache-replay-b8.json)。

## 优化优先级

1. **收敛执行形状并改善 Graph 覆盖。** 评估安全的行数/分组分桶、代表性预热、按节省时间选择捕获形状。分桶只增加执行填充，不扩大逻辑草稿预算；填充行必须不写真实 KV、不进入验证或在线反馈。不能直接把 key 中的 R 改成 bucket(R)，因为当前 KV 写入和索引还依赖真实行数。只增加图数会占用更多显存，不作为唯一方案。
2. **减少共用后端的元数据上传和 GPU→CPU 往返。** 复用一个树状态内不变的拓扑/位置元数据，合并批次 readout 的排序、top-m 和结果提取。验证需覆盖槽位回收、并发补位、EOS、top-m 并列值和逐 token 输出；BF16 差异不能默认视作无害。
3. **将实时共享历史作为明确命名的独立消融。** 保持 Q/N 与在线规则不变，另查融合方法中候选变化、有效覆盖与运行时间。当前回放仅针对确认前缀上的根查询，没有评估模型孩子的假设前缀查询。
4. **最后精简空树检索和完成时的重复索引。** 保持现有完成后共享语义，先验证候选 token、parents、probs、score 完全一致，再评估工程收益。

本轮仅完成诊断，没有宣布端到端提速，也未启动新的正式实验队列。

## 补充：草稿数量、检索命中与接受率

针对“纯后缀是否尝试了更多后缀、是否参数未对齐”的核查，重新汇总了全部 B1/2/4/8/16 的现有逐题日志，未重跑全量生成。机器可读结果见 [alignment-and-yield.json](../results/loopfill-suffix-diagnostic-20261104/alignment-and-yield.json)。

三组 budget-suffix/raw/online 的 Q=4、N=16、factor=1、min_token_prob=.001、树检索模式及完成后共享缓存策略一致；缓存实现文件哈希也一致。raw 与纯后缀系数均为 1，online 初值 .7 是方法本身的区别。纯后缀没有浅层模型提案或模型孩子查询，预算 N=16 在这里不限制实际草稿，不能把“预算相同”解释为“实际并行节点相同”。

| 已有 B8 全量结果 | 纯后缀 | raw | online |
|---|---:|---:|---:|
| 后缀查询次数 | 30,775 | 275,667 | 265,203 |
| 其中根查询 | 30,775 | 32,933 | 34,566 |
| 其中模型孩子查询 | 0 | 242,734 | 230,637 |
| 选择事件处平均草稿节点数 | 1.80 | 13.56 | 13.72 |
| 峰值草稿节点数 | 4 | 16 | 16 |
| 未接受节点所耗 rows / 全部 rows | 37.52% | 58.83% | 56.95% |

纯后缀确实有无效验证，但不是因为给了它更大的 Q 或让它查询更多。融合方法也有大量浪费，不能只用浪费比例解释速度。

纯后缀的已分配节点全部跑满 32 次循环。逐题核对了 `rows = nodes * 32`、`steps = speculate_calls`、`selected_draft_nodes_sum = 2 * (nodes - speculate_calls)` 以及 `(nodes - speculate_calls - covered_tokens) * 32 = wasted_rows`。据此，纯后缀每次根查询的新草稿数、接受数和浪费量可从正式记录精确恢复：

| B | 平均草稿数 / 查询 | 草稿节点接受率 | 未接受节点所耗 rows 占比 |
|---|---:|---:|---:|
| 1 | 1.798 | 40.14% | 38.46% |
| 2 | 1.780 | 39.53% | 38.72% |
| 4 | 1.759 | 38.27% | 39.35% |
| 8 | 1.801 | 41.65% | 37.52% |
| 16 | 1.764 | 40.12% | 38.22% |

B8 提出 55,440 个草稿节点，23,089 个接受、32,351 个未接受。后者占草稿的 58.35%，耗费 1,035,232 rows。分母若包括确认根的全部计算，则是 37.52%，两个比例不能混用。纯后缀每输出 token 约 50.86 rows，高于同 B 的 AR 约 31.71 rows；节省串行推进次数的收益需要抵消这部分多算的工作。raw 的 `from_suffix` 只是节点最初来源，存在候选合并与后续重评分，不能直接当作所有 suffix 候选的接受数。

正式旧日志没有记录“返回非空候选的查询次数”。新增 [实际检索命中诊断](../scripts/loop_suffix_hit_diagnose.py)，使用同一 B8 前 32 题、每题最多 64 新 token、正式预热题序，不更改解码器。只包装 cache 查询并使用已有 child-query observer 分类。两组的 32/32 条输出及 calls/rows/queries/covered 计数，均与前一轮相同短流的诊断结果完全一致。

| 32 题短诊断，非全量命中率 | 非空查询 / 总查询 | 检索非空率 |
|---|---:|---:|
| 纯后缀根查询 | 572 / 963 | 59.40% |
| raw 根查询 | 616 / 1,005 | 61.29% |
| raw 模型孩子查询 | 4,969 / 8,728 | 56.93% |

结果见 [纯后缀命中统计](../results/loopfill-suffix-diagnostic-20261104/retrieval-hits-b8/budget-suffix-b8-suffix-hits.json) 与 [raw 命中统计](../results/loopfill-suffix-diagnostic-20261104/retrieval-hits-b8/budget-raw-b8-suffix-hits.json)。该短流冷启动、输出较短，不能冒充完整 480 题的缓存命中率，也不能与先前“每个已确认前缀都查询”的合成回放比例混用。

检索非空率、候选接受率、CUDA Graph 命中率是三种不同指标。59.40% 是查到了候选；41.65% 是全量纯后缀草稿节点最终被接受；1.62% 是全量 B8 纯后缀模型调用走了已捕获的 CUDA Graph。

进一步看短诊断的根查询，纯后缀 410 次只匹配一个历史 token，其中 98 次覆盖了真实下一个 token（23.90%）；匹配长度至少 4 的 37 次查询，27 次覆盖（72.97%）。两个组的一 token 匹配子集在该样本中统计相同。仅降低最大草稿长度可能损失较可靠的长匹配收益；固定 Q=4，单独研究弱匹配是否应该放弃投机更有针对性，但尚未证明筛选后的端到端提速。该短样本纯后缀返回的 854 个节点中，仅 3 个缓存路径概率低于 .1，因此也不能预设只把概率阈值 .001 改成 .1 就能消除主要浪费。
