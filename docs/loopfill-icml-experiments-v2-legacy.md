## 1. 论文范围与完成标准

论文定位为**循环语言模型上的免梯度训练投机解码方法**：让后缀候选与早期循环读出共同扩展草稿树，再以经验匹配率和路径阈值控制额外计算。主张范围是贪心解码、两个循环架构、固定 batch 原型。统计校准的数据与计算成本必须报告；“免训练”不能写成“零准备成本”。

要形成完整证据的论点：

| 论点 | 必须提供的证据 | 实验 |
| --- | --- | --- |
| 算法按已验证前缀的全深度预测提交 token | 精确算术下的论证；独立官方 forward 对照；真实模型 FP32 检查；BF16 分歧诊断 | E00、E03 |
| 低负载下减少真实端到端时间 | 同硬件/同后端的 AR、WFD、纯后缀、两个 C；完整输出及耗时 | E01 |
| 额外候选计算影响高负载吞吐 | B 扫描覆盖平台或明确的显存边界；各方法可行范围、真实行数及峰值显存 | E01、E08 |
| 收益来自两种来源的接续、剪枝和再次读出 | 单因素开关；相同题序与缓存协议；真实墙钟和计算量并列 | E05 |
| 统计评分与阈值有实际作用 | 校准外可靠性、支持数、阈值/预算敏感性及校准成本 | E06、E08 |
| 在不同于校准数据的任务上仍有用 | 数学答案正确率、代码编辑测试通过率、任务耗时；保留失败样例 | E03、E04 |
| 与最接近的已有工作有清楚关系 | 官方 LoopSpec 与 WFD 直接实测；各自 AR；明确后端和计时差异 | E02 |
| 后缀复用协议符合真实可见历史 | 本题/跨题历史消融、真实二轮会话及发布顺序 | E07 |

“数据完成”指矩阵中所需单元有完整成功产物或可解释的预登记不可行状态，统计和图表可从原始记录重建。**不要求结果全部正向，也不以超过某个加速倍数作为完成条件。** 出现劣势、质量下降、显存受限或外域校准失效，要进入结果与论文边界。

这套设计依据 ICML 对论点支持、实验合理性和可复现性的要求组织，并非官方规定必须做这些数据集或实验数量。[审稿说明](https://icml.cc/Conferences/2026/ReviewerInstructions)、[作者说明](https://icml.cc/Conferences/2026/AuthorInstructions)。当前核对的是公开的 2026 指南；目标投稿年的格式、匿名政策和截止日期需在正式提交前重新核对，不沿用旧年份日期。

## 2. 模型、数据、划分与公共设置

### 模型和硬件

- **两个主模型固定**：Ouro-2.6B，T=4、(d₁,d₂)=(1,2)；Huginn-3.5B，T=32、(4,8)。权重 revision 沿用 batch 子协议。二者覆盖整栈循环与 prelude/core/coda 两种结构；结论限于这两种已测架构。
- **主硬件固定**：本机单张 NVIDIA L20X，约 140.4 GiB。两个模型可分配相同型号的不同卡并行；同一模型的配对比较固定 GPU UUID。8 张卡不作为一次单卡实验的总显存。
- BF16 是主吞吐精度；FP32 仅用于正确性和数值诊断。固定 target 深度、初始化、chat template、停止符、精度、attention 策略及编译开关。没有量化、跨循环 KV 近似共享或训练新 drafter。
- 主后端继续使用当前固定 batch：合并投影/MLP/读出，逐请求 attention，串行 prefill，完成槽空闲。计入这些开销；不声称是完整 serving 或硬件理论峰值。先完成必要的缓存容量修正，再冻结源码，所有 B 在最终代码上重跑。

外部校准源固定为 UltraChat revision `8049631c405ae6576f93f445c6b8166f76f5505a`；先做提示去重和两 tokenizer 的完整预算检查，再按 `SHA256("20261103:"+prompt_id)` 排序，前 128 个构成嵌套校准池，接下来的 192 个构成开发池。主表仅拟合前 64 个。具体规则和待生成路径见[校准登记](../results/loopfill-icml-20261103/calibration-policy.json)，来源的 `train_sft` 划分见[数据卡](https://huggingface.co/datasets/HuggingFaceH4/ultrachat_200k)。64 是事前预算，不是已经验证的充分样本量；须报告真实 token 数、各分箱支持数及回退比例。

**标准评测依据**：SuffixDecoding §4.1/§4.2 与附录 A.1 描述使用标准 Spec-Bench 数据和原仓库评测框架，未描述 420/60 校准切分；官方 `question.jsonl` 实查为 480 个唯一请求，且与本仓库文件 SHA256 相同。因此按其公开协议应以完整 480 个请求为评测集合；该结论不冒充对作者未公开逐请求运行日志的覆盖审计。其后缀概率来自在线历史频次，不是我们额外拟合的 full-depth 命中率表；论文也报告了 hybrid 阈值敏感性，不能据此声称作者完全未做任何基准参数探索。[SuffixDecoding](https://arxiv.org/html/2411.04975v3#A1)、[官方题库](https://github.com/hemingkx/Spec-Bench/blob/main/data/spec_bench/question.jsonl)。

提示与评分也已选定，见[评测协议](../results/loopfill-icml-20261103/evaluation-policy.json)：MATH 使用固定零样本 boxed 提示和 pinned Math-Verify（解析/等价验证各限 5 秒）；CanItEdit 使用官方 zero-shot chat 模板、首代码块抽取及固定版本测试环境，每程序 60 秒、1 CPU/4 GiB，无重试修改代码。测试前先核对参考程序能通过官方测试，冻结环境与镜像 digest。这里的资源限制是本实验设置，不冒充官方默认。[Math-Verify](https://github.com/huggingface/Math-Verify/tree/ba3d3aaff23b3f4cac7a14672b4f6e293d97c98b)、[CanItEdit 评测说明](https://github.com/nuprl/CanItEdit/tree/74d15ea7e6207cb9fdeeecd761907371d4cc2e26/benchmark)。适配代码尚待实现；只在开发阶段解决兼容性，不能按正式得分反复换提示/判分器。

**泄漏与覆盖规则**：

1. **正式实验只使用外部小样本校准表**：Spec-Bench 全部 480 题及其任何输出、读出、命中标签和历史都不得进入校准；旧 dev420 标签不构成例外。offline、joint 与 insitu 表均从对应外部校准子集拟合；开发池只作诊断和选参。原脚本共享 dev/confirm 历史的问题仍需修复，但只修这个问题不足以支持全 480 评测。分箱、读出、τ、样本预算在新评测前冻结；两个主 τ 均报告，不按测试结果选优。
   外部重拟合消除了新表与评测集的直接拟合重叠，不能将已经影响过方法设计的 Spec-Bench 重新称为未见盲测。旧结果保留为探索，泛化边界由独立任务补充。
2. 校准/开发候选与完整 Spec-Bench（包括二轮）、MATH-500、CanItEdit 做 ID、标准化文本和近重复检查；移除重复的**校准/开发候选**并按冻结顺序补位，不通过删评测题制造隔离。外部评测集之间的重复另行登记并报告覆盖。基础模型预训练污染未知，不声称排除了它。
3. 先用两个 pinned tokenizer 检查完整提示+全部输出预算+草稿余量。超上下文时按输入长度事前登记共同可行集合；不得按实际回答短、成功率、速度或显存运行结果筛题。代码任务不能静默删掉部分 before 程序；二轮若包含自身回答后超窗，保留为预算超限失败，不从分母删去。
4. CanItEdit 的 12 题只用于适配模板、抽取程序和验证评测环境。正式 93 题在模板/规则冻结后运行；即便开发题通过率低，也保留正式结果，限制任务收益的表述，不事后换题集。
5. 主实验历史从空缓存开始；本题已验证输出可本地查询，跨题只加入本方法在当前评测流中已经完成请求的输出。不得预装校准/开发输出、评测参考答案或离线 AR 输出。在线后缀缓存可按该协议更新，但校准概率表在整个评测期间只读；统计校准与测试时缓存分别登记。

### 预先固定的工作点

主方法同时报告 C(0.01) 与 C(0.1)，不按测试 B/任务事后挑最佳阈值。top-m=8，后缀最大草稿 64，主树容量 1024 节点/请求。使用 G1 在外部 64 提示上分别拟合并冻结的 joint/insitu 表、剪枝、接受即更新及新孩子后缀查询。两模型使用相同提示 ID、各自目标输出与校准表；所有 B 使用同一算法配置。

`max_seq≤4096` 是位置容量上界，不必每槽盲目预留 4096。全量分词后按固定分配规则减去不用的容量；所有方法的逻辑上下文/输出预算一致，树方法的逻辑节点上限一致。AR 不为完全不使用的草稿预留 1024 节点。WFD 按实际在途节点需要分配，其他方法按登记上限分配。分配若发生在计时流内必须计时。**此项是投稿前必补的轻量实现，不要求 paged attention。**

## 3. 必做实验矩阵

### E00：正确性与正式运行资格

- 先在外部开发提示核对官方 AR reference，再完成外部 64 提示校准，最后进行五臂真实模型检查。使用完整首轮提示、最多 1024 新 token、自然 EOS、冻结 hash 顺序与冷历史；拟合过程中只发布当前校准子集已完成请求的输出。本题已验证输出可本地查询。禁止复用 Spec-Bench 的任何读出/拟合表/候选日志；各样本量可以复用兼容的外部 AR 读出，但候选历史和拟合过程必须各自重建。新输入和表均尚未生成。
- 先运行现有 CPU/CUDA 小模型测试，再对两套真实 checkpoint 在外部 check12、FP32、B=1/2、64 新 token 下检查五臂输出；另做外部 validation32、B=1/2、256 新 token 的 FP32 扩展检查。这里只截生成长度，不裁提示。
- 独立核对官方模型 forward 的全深度 logits：每模型从 check12 选覆盖短/长提示的 6 题，对至少 16 个连续前缀比较 argmax、max/mean logits error、前两名间隔。Huginn 必须使用同一按位置固定的初始 latent 与 recurrence/cache 配置。
- 覆盖 EOS、只生成一词、最后不足 B、长短混批、回退、触顶、槽位复用、后缀完成后发布。已有小模型覆盖这些边界；真实模型另用预定 3 条请求、B=2 检查尾批及跨槽隔离。
- FP32 分歧阻止正式计时。若差异源于浮点近似平局，保存共同前缀诊断，修复或在理论/实现描述中明确条件；不能仅因模型相同就当作实现正确。BF16 全文一致性不足不能自动归因于数值误差。
- reference 检查使用 eval/no-grad，关闭 dropout 和 TF32，记录 attention/矩阵乘精度开关。精确算术证明需明确提交规则、回退与重定位不改变已验证前缀，以及草稿评分/剪枝只影响额外计算，不改变目标贪心选择；本轮不外推到随机采样的分布保持。
- 完成条件：测试日志、独立 reference 对照、配置快照、预检逐题结果齐备；没有未解释的状态/KV/调度错误。

### E01：主端到端与 batch 吞吐

**矩阵**：2 模型 × 5 臂（AR、同引擎 WFD、同引擎纯后缀、C.01、C.1）× 各模型/方法可行 B × 3 题序 × 2 计时重复。正式流为合规 Spec-Bench 首轮全集；B=1 同时提供单请求结果，不重复开另一套不同历史实验。

- B 候选 1,2,4,8,16,32,64；64 仍明显上升且容量允许时扩至 128。开发探测使用固定 load192；扩至 128 时先登记至少 384 条独立开发请求。**先确认真有 B 条请求活跃，不能用 24 条请求测“B=32”。**
- 候选平台：连续两次翻倍吞吐增幅各低于 5%，在相邻三个 B、相同题序各独立重复三次后确认；噪声相近则继续。这个阈值是本项目的操作规则。先遇容量限制时标注“显存受限，未验证吞吐平台”。
- 一臂 OOM 只结束该臂更大 B 的尝试，保留其他臂范围；主图在共同 B 比较，另列各臂已测最高吞吐及 B。所有点包含低于 AR 的结果。
- 正式题序 seeds=0/1/2；每题序计时重复 r=0/1，缓存均重新冷启动，预热缓存丢弃。固定方法轮换，第二次重复反转执行顺序以减小温度/时钟漂移。重复编号不是新的生成 seed。
- 全部 480 题属于评测集，包含 Huginn 旧读出缺失的 253/288/295；逐 ID 审计覆盖。因上下文确实无法运行而采用共同可行子集时，明确实际 N 与失败/排除原因，不称完整 480。原确认 60 题可作历史分组诊断，不再另设必做吞吐流或作为唯一校准外分母。
- 提供全量及六类的输出长度/逻辑计算统计；若要报某类别的独立吞吐，必须单独跑该类别，不分摊共享流时间。

**主指标**：实际输出 token / 整流墙钟；附 request/s、请求服务延迟 p50/p95、TTFT、峰值显存、实际 core calls/rows、行数/token、触顶请求比例、输出上限比例、BF16 一致率。全流计时含 prefill、树/后缀处理、调度、验证、EOS 与尾批。模型/初始缓存分配、tokenization、warmup 在计时外。

### E02：官方强基线与引擎对照（必做）

| 实现 | 模型与方法 | 正式设置 |
| --- | --- | --- |
| 当前后端 | AR、WFD、Suffix、C.01、C.1 | 复用 E01 B=1 |
| 官方 WFD | Ouro/Huginn：AR、WFD；保持完整 recurrent KV | 同一物理 GPU、对应 checkpoint、相同 tokenized 输入、BF16、贪心、1024 输出 |
| 官方 LoopSpec | Ouro-2.6B：原生 AR、single-proposal (d₁=1)、dual-proposal (1,2) | 同上；B=1；保持作者支持的 CUDA Graph/优化并记录版本 |

每条基线用合规 Spec-Bench 全集、3 题序×2 重复。先用 check12/pilot24 验证协议、停止条件和目标 forward；不同环境可隔离运行，不迁移 LoopFill。官方 LoopSpec 的 Raven 检查点不等于本项目 Huginn，不能混名作直接对照。若本项目后端与官方代码的 target 语义无法对齐，记录原因、先解决，不能宣称强基线已完成。

再在 CanItEdit 正式 93 题为 Ouro 加官方 LoopSpec dual-proposal 与 native AR，B=1、2048 输出、3 题序×2 重复；与 E04 的当前后端 B=1 配对展示。这使最近方法的直接对照也覆盖校准外任务。

同时报告绝对 tok/s、wall time、输出数、各引擎原生 AR，以及方法相对其原生 AR 的比值。**跨引擎“相对 AR 的倍数”只能解释局部收益，不能相除得到对手绝对加速比。** 若官方 LoopSpec 绝对速度更快，主文保留，结论限于算法/原型结果；不得只报告较弱的同引擎 WFD 来代替。

不新增 DFlash/EAGLE 训练：本轮比较免梯度训练方法，没有兼容 checkpoint 的训练型 drafter 就不自造配置。只有将论文主张扩为全面优于训练型方法时，才需另立实验。

### E03：BF16 质量与跨域验证

- MATH-500 固定零样本用户指令，要求最终答案用 `\boxed{}` 表示；最多 2048 新 token。与 LoopSpec 论文印刷表的 few-shot 数字不混用。
- 2 模型 × 5 臂 × {B=1, `B_math`}；`B_math` 取 E01 共同网格中，在该任务完整提示+2048 输出预算下通过容量核验的最大值。只使用输入长度和分配上界确定，不读取质量分数选择 B；若实测 OOM，按预登记顺序降一档并保留失败单元。算法参数不得在 MATH-500 上调优。一个预定题序 seed=0，greedy；每题一个答案。此批用于质量，不凭单次计时作稳定性能主张，质量结论限于实际评测的 B。
- 固定公开数学答案提取/等价判断器版本、超时及无法解析规则；抽样人工核对解析错误。保存最终答案、判分理由、超时/截断/格式错误。不存在答案或运行失败也留在分母。
- 对每臂报告准确率、相对同 B AR 的配对差值及 95% 区间、逐题全文一致率、首个分歧和长度差；另将 B>1 AR 对 B=1 AR，分离 batch 数值效应。
- 对全部分歧记录首个位置；按预登记 ID/hash 顺序每模型取最多 30 个分歧题，复放共同前缀并检查 FP32/BF16 full-depth logits、top-2 margin、缓存和 mask。若少于 30 则全查，不能只挑近似平局样例。
- “未显著下降”不等于等价或无损。报告区间允许的下降范围；只有事前定义并有依据的非劣界限被满足，才作非劣表述。本计划不以任意百分比容忍度替代算法正确性。

### E04：真实代码编辑：速度与正确答案同时报告

- CanItEdit 使用明确描述、before 原程序和模型自身 chat template；要求返回完整修改后 Python 程序。使用官方代码抽取/测试机制，冻结其版本与适配差异。
- 12 开发题按官方 `adaptive/corrective/perfective` 各 4 题预选；冻结模板、代码抽取、依赖与超时后，只对其余 93 题报告正式结果。开发题通过率低也不会触发事后挑题或切换更有利任务。
- 正式矩阵：2 模型 × 5 臂 × {B=1, `B_edit`} × 3 题序×2 重复。`B_edit` 取 E01 共同网格中不超过 16、且完整输入+2048 输出预算可容纳的最大 B；容量选择只看输入/分配上界，不用正式得分或 speedup。93 题在 B=16 时仍有五个完整批次。12 开发题不被当作 B=16 的满批性能验证；全 B 分配核验与正式流另行进行，实际 OOM 则按预登记降档并保留失败。此批验证外域实用性，最大硬件吞吐结论来自 E01/E08。
- 测试在隔离执行环境、固定资源/超时下运行；测试耗时不计模型吞吐，另列任务完成总耗时。评分只读生成程序；不把 tests/after 放进提示、后缀历史或重试循环。
- 报一次 greedy 作答的程序测试通过率（greedy pass@1）、生成 tok/s、request/s、正确解决程序数/生成墙钟、截断/语法/测试失败率，以及 accepted suffix/fill 来源统计。计时重复不增加 pass@k 的样本数。
- 全任务分母包含错误和失败；不同文本但同样通过测试可以接受，不能以文本一致替代功能正确。只声称加快程序编辑请求，不声称加快整套 SWE-bench agent 修复。

### E05：核心机制消融

固定 load192，两个模型，B=1 和该模型 E01 的最高共同 B（相同数据流）；3 题序、每题序一次计时。以 C.01 为母配置，以下变体逐个改变规则：

| 变体 | 精确定义 | 可以归因的内容 |
| --- | --- | --- |
| C.01 | 完整方法，作为本批配对对照 | 本批基准，不混用不同输入/运行协议的 C |
| no-suffix | 关闭所有后缀草稿，保留 early top-8、联合打分、剪枝 | 后缀来源的整体贡献 |
| suffix-only-calibrated | 关闭 early 提案与 early 重评分/剪枝，保留后缀路径评分、全深度验证与已提交根续查 | early-loop 来源与更新的整体贡献；不是官方 SuffixDecoding 性能复现 |
| no-child-query | 只关闭新模型孩子立即查询后缀；保留已验证根查询、接受即更新、early 提案、联合打分与剪枝 | **两种来源提前接续**的增量贡献 |
| no-prune（B） | 保留联合打分和入场阈值，只取消已有节点因重评分而被删除 | 动态剪枝的计算与墙钟收益 |
| no-d₂（E） | 去掉第二次读出，保留第一次评分与剪枝 | 第二次读出的整体收益/成本，不能只归因于新增孩子 |

每次报实际 token/s、core calls/token、rows/token、readout/coda 行数、后缀查询次数/耗时、删除节点数、cap skips、输出一致率。路径来源可能重叠：保留初次入树来源与后续来源标记，避免一个接受 token 被多次计为“新增贡献”。

现有 CPU 回放可补 top-1、K=16、读出深度及 joint 重评分的更大矩阵，但不能用估计的 off-path 行数替代此处真实 GPU 行数。触顶会改变 no-prune 的行为，报告触顶比例并配合 E08 大容量 B=1 复核，不能把被容量剪掉的节点算作算法主动剪枝收益。

### E06：阈值、校准和离线准备成本

1. **阈值四点**：τ=0.01/0.03/0.1/0.3，load192、两个模型、B=1/最高共同 B、3 题序×1。画真实吞吐—rows/token 与调用数的取舍。两条主方法预先固定为 .01/.1，其他点是敏感性，不用于挑测试最优曲线。
2. **评分对照**：在 C.01 上只把 suffix 的 insitu 表换为相同外部 64 提示拟合的 offline 表；其余完全相同。用外部 load192、两个 B、3 题序测墙钟/行数；与 E05 对照可合并调度。
3. **校准外可靠性**：全部 Spec-Bench 480 + MATH-500，记录位于真实贪心路径上的候选预测分数与实际匹配事件；只作最终测量，不用于重拟合或选参。固定十个等宽 bin，报告支持数、Brier、ECE 和 reliability diagram；另按来源、深度、match length 展示。多候选不是独立题目，区间按请求聚类。外部 validation32 是开发诊断，不能混入正式测试指标。
4. **路径分数校验**：在深度 1/2/4/8 的候选路径检查“所有 token 均与全深度 greedy 一致”的频率，区分 edge 匹配率与路径成功率；分数乘积不自动等于独立事件的真实概率。off-path 近似读出不能充当校准真值。
5. **样本效率**：固定外部 16/32/64/128 个嵌套提示，各自从空历史拟合，在外部 validation32 比较支持数、回退比例、可靠性与 calls/rows。保持读出、τ、分箱不变；小样本拟合不得读取大样本的候选历史或表。主配置事前固定 64；如需修订，必须在新评测前依据外部开发证据登记，不能看 Spec-Bench/MATH 结果决定校准规模。
6. **成本**：完整登记两模型外部校准的请求数、实际生成 token 数、读出 GPU-hours、CPU 拟合时间、表大小及来源；主 64 提示与扩展到 128 的诊断成本分别列出。每模型主参考生成最多 65,536 新 token，这不是运行时间保证，也不把每个候选当作独立请求。报告无梯度训练，同时说明统计准备开销；任何摊销估计写明工作负载和假设。

可靠性与详细来源日志使用独立诊断运行；正式吞吐只保留低开销计数，不能把 profiler/大量逐节点日志运行与普通计时混合。

### E07：历史复用与二轮请求

- 80 个 MT-Bench 会话，两个模型、五臂，B=1 和 `min(8,B_common)`，3 会话题序×1。第一轮全部生成后，第二轮依赖各方法各自第一轮答案；相同会话序，同一模型内各臂一致的入场规则。固定两个阶段的批处理，不实现持续补位。
- 本方法同时比较“prompt+自身已验证输出”与“再加完成请求输出”的缓存模式；对纯后缀和两条 C 测两种历史，AR/WFD 只跑一次可复用。两模式均从冷缓存开始，不预装测试答案。
- 报第一轮、第二轮、整个 160 请求流的时间/实际输出、匹配长度、查询命中、接受来源、CPU 索引内存/查询时间。全会话耗时以实际执行为准；阶段 barrier 与超窗失败明确计入。
- 二轮输入里包含自己的第一轮答案，故允许复用；不同方法的 BF16 第一轮差异会影响二轮难度，保留全部结果并报告差异，不只保留共同回答子集。此批只说明对话复用，不作满载上限证据。

### E08：容量、上下文与实现开销

- **节点预算**：512/1024/2048/8192，pilot24、两个模型、两条 C、B=1、1024 输出，3 题序×1；计触顶、输出、行数、显存、吞吐。主图仍固定 1024；不按结果换有利预算。
- **上下文敏感性**：输入 P=128/512/1024/2048、输出上限 256，真实模型核验；2 模型×{AR,C.01,C.1}×{B=1,四个 P 共同可运行的 B_ctx}×3 题序×1。固定 192 个唯一开发文本片段，按预登记规则构造精确 token 长度；各方法用同一输入，不模拟接受率。该受控任务独立命名，不当成自然 Spec-Bench 分数。
- **容量先到而平台未到**时，在上述短上下文设置扩大 B，展示模型计算/调度随 B 的变化；不能用这个短任务的高 B 结论替换完整提示的 E01。真实 EOS 下空槽仍需报告；也不能声称所有时刻持续满载。
- **性能分解**：每模型在 B=1 与平台/最大共同 B，从 load192 的固定顺序选前 `max(12,B)` 个不同请求，输出预算 256，单独 profile AR、WFD、Suffix、C.01、C.1。确保高 B 至少有一个真实满批；不以该短 trace 证明持续满载。拆 prefill、core、attention、lm_head/coda、CPU tree/suffix、同步/空闲；不能把并发区间或 CPU/GPU 重叠时间相加凑成 100%。同时保存无 profiler 的对应墙钟。
- **BF16/FP32**：不要求全量 FP32 性能曲线；E00 的真实 FP32 对齐与此处诊断足够支撑数值边界。没有确定性实现/证明时，不宣称有限精度下逐位无损。

## 4. 统计方法和公平比较

**吞吐**：每次完整流计算 `Q=sum(actual_output_tokens)/wall_s`，包含第一词和实际返回的终止 token，不含 prompt。每个 seed/rep 配对计算 `Q_method/Q_baseline`。同 seed 的两次先汇总，再等权汇总三个题序；保留所有六个点、均值、标准差/范围。图中误差线标清是题序范围或运行波动。3 个题序不足以伪装大样本 95% 置信区间；不从并发逐请求 `decode_s` bootstrap 整流吞吐。

**单请求时间**：B=1 的逐题 wall/服务延迟与总体吞吐都报。BF16 输出长度可能不同，“完成相同请求的时间比”与“token/s 比”分别标注。共享历史会耦合请求，主要性能不确定性单位仍是整流；固定缓存、独立请求的诊断才可做题级配对 bootstrap。

**质量**：对 MATH-500/CanItEdit 的唯一问题做配对 bootstrap 10,000 次，bootstrap seed=20261103，报告准确率/通过率差值的 95% 区间及两种不一致计数；小样本另外给配对离散数据的区间/精确检验，不把零观测差异解释为无限精确。多个题序/计时重复按同一问题聚类，正式主质量表用事前指定 seed=0、rep=0，其余作为稳定性附表。若做多项显著性检验需调整并声明；主结果以效应量和区间为主。

**公平性**：固定硬件、目标模型语义、提示/停止规则、token 预算和任务覆盖；算法特有参数明确列出。相同逻辑节点预算不等于要求 AR 分配无用空间。没有对应同 B 基线的点只报绝对吞吐，不外推 speedup。不同引擎的 CUDA Graph/attention 优化和网络开销单列，不将服务器网络计入一侧而只计内核于另一侧。

**失败与重跑**：OOM、节点触顶、上下文超限、超时、质量失败分开。失败请求不从质量分母删去；未完成流不纳入成功流吞吐。只有硬件干扰/进程异常等事前规定原因才重跑，在相同配对 block 重跑并保留原记录；不得仅因某次慢而删记录。保存早先失败、重试原因和最终采用的 run_id。

可以两模型各固定一张 GPU 并行；官方引擎顺序占用对应模型 GPU，以免同卡干扰。其他空闲卡可做不与计时争用 CPU 的 reference/诊断/评分；并行增加至更多卡时，所有比较按 GPU block 配对并保存映射，不能把不同卡上的一次最快运行拼成主表。

设某模型/方法测试的 B 数为 `k_m,a`，E01 全量正式流数是 `6×Σ(k_m,a)`；若两模型五臂均有 7 个 B，则为 420 流、201600 次请求生成；不再另加原 confirm60 流。E02 的 Spec-Bench 为官方 WFD 两模型各两臂加 LoopSpec 一模型三臂，共 7×6=42 流，CanItEdit 官方 LoopSpec/native AR 另加 12 流。E03 至多 20 流；E04 至多 120 流；相同 B=1/高 B 时合并。

E05、E06、E07、E08 的数量按[实验矩阵](../results/loopfill-icml-20261103/experiment-matrix.json)逐项计算，重复 run key 可复用，输入/历史/后端不同则不可复用。GPU-hours 必须由 G2 当前机器的实测成本估算：按每类请求长度、实际 batch 空槽和各臂完整流计时计算，并单列失败重试及诊断预算；不沿用旧机器的秒/题给出虚假的完工日期。若资源需要压缩，优先减少辅助敏感性重复或把非核心细图移附录，保留主基线、质量、核心机制与负面点。

本计划不安排训练新 drafter、连续到达/SLO 服务、分布式引擎改造、完整 SWE-bench/SQL agent 系统或额外模型家族。这些都不是本论文当前主张的数据前提。若未来扩大主张，先扩展矩阵与协议，再开展实验。
