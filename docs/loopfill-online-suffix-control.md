# LoopFill：固定节点预算与在线 suffix 权重调整

日期：2026-11-04。

本文记录新的算法设计：**每个 request 最多保留 N 个未接受的草稿节点；每当一个父节点到达已确认前缀并完成全深度验证，就用它下面已有的后缀候选记录，小幅更新一次 suffix 权重。** 不攒固定数量的反馈，不训练分类器，不读取离线校准表。

实现状态（2026-11-04）：[预算解码器](../src/llm_memory_editability/loop_budget_decode.py)已实现本文算法，并接入单请求与固定 batch 入口；[旧阈值解码器](../src/llm_memory_editability/loop_prob_decode.py)保留用于历史复现。尚未运行新版的全尺寸 480 题性能评测，历史结果不改名。当前接口和下一轮实验配置见第 11 节。

## 1. 用一句话理解整个算法

模型浅层读出和 suffix tree 一起提出候选；修正后的路径分数决定谁占用 N 个名额；全深度模型决定实际输出；已经得到的验证结果再帮助调整下一轮的 suffix 权重。

```text
模型浅层读出 ─┐
              ├→ 候选并集 → 计算路径分数 → 每请求保留最多 N 个 → 提前计算
suffix 检索 ──┘                 ↑                               │
                               │                               ↓
                         更新 suffix 系数 ← 记录预测误差 ← 全深度验证
                                                               │
                                                               ↓
                                                        提交 token、前移根
```

这里有两个互相配合的机制：

- **N 管数量：** 当前请求最多给多少个草稿节点分配提前计算的机会。
- **suffix 系数管排序：** 当后缀分数整体偏高或偏低时，调整它与模型候选竞争名额的能力。

控制器不修改 N，不规定 suffix 必须占多少名额，也不决定最终输出。

## 2. 第一版维护哪些量

| 符号 | 含义 |
| --- | --- |
| N | 每个请求允许保留的未接受草稿节点数上限 |
| q(v) | suffix 检索返回的条件边分数 |
| p_d(v) | 父节点在模型深度 d 读出时，对候选 token 分配的 softmax 值 |
| c | 当前请求的 suffix 修正系数，初始为 1 |
| u = log c | 系数的对数，便于更新且保证 c 为正 |
| e(v) | 当前实际用于排序的条件边分数 |
| S(v) | 从当前已确认根到节点 v 的路径分数 |
| eta | 每次反馈的调整步长，越小调整越慢 |

**第一版实现选择：每个 request 独立维护 u，开始时 u=0，结束后丢弃。** 本请求只使用自己已经得到的验证结果更新系数。这样不额外引入控制器状态的跨请求传播；短请求可能来不及充分适应，这是这个选择的代价。已有 suffix 历史缓存仍遵守原先的隔离与发布规则。

第一版只用积分反馈，也就是“在上一次系数的基础上继续小幅纠偏”；不引入比例项 P 或微分项 D。

## 3. 两种候选怎样评分

每条边同时保存原始分数和当前评分来源。候选曾经来自 suffix，不代表它以后永远使用 suffix 分数。

\[
e(v)=
\begin{cases}
\min(1,c\,q(v)), & \text{当前评分来源为 suffix},\\
p_d(v), & \text{当前评分来源为模型读出}.
\end{cases}
\]

系数为 0.6、后缀原始分数为 0.9 时，调整后的边分数就是 0.54。截断到 1 是为了让所有边分数保持在 [0,1]。

根分数为 1，其他节点沿路径相乘：

\[
S(\mathrm{root})=1,\qquad
S(v)=S(\operatorname{parent}(v))\,e(v).
\]

例如模型边 A 的分数为 0.6，A 后面的 suffix 边 B 的原始分数为 0.8，当前 c=0.5，则：

\[
e(B)=0.5\times0.8=0.4,\qquad S(B)=0.6\times0.4=0.24.
\]

模型读出到来时，用本次模型分数替换这条边的旧分数。之后更深读出再替换浅层读出。**同一条边的前后两轮分数不相乘；不同位置的边才沿路径相乘。** 再次检索到已有模型评分的孩子，不把它改回 suffix 评分。

修正发生在每条仍使用 suffix 评分的边上。因此，若一条路径有 m 条这样的边，在未发生截断时，它会包含 c 的 m 次方。长后缀路径受影响更大，这是逐边修正的结果，需要在实验中观察。

模型仍以全词表 softmax 提出 top-8，不对这 8 个值重新归一化。现有代码对部分 top-8 外已有孩子使用 ABSENT=0 的启发式；本方案不把这个零解释为真实概率，也不声称已经修复它。改为提取所有已有孩子的真实 softmax，是另一个可单独实施与评估的改动。

## 4. 固定 N 怎样选择候选

每次扩展或重评分后，把现有节点和本轮新候选放在一起，按路径分数 S 从高到低保留最多 N 个。

- prompt、已确认前缀和当前已确认根不占 N。
- 尚未被接受的节点都占 N，包括已经算完全深度、但还在等待前缀确认的节点。
- 同一父节点下相同 token 合并；不同父路径上的相同 token 是不同节点。
- 保留一个节点时，必须保留其未接受的祖先，不能留下断开的子树。
- 同分时先保留更浅的节点，再按根到节点的 token ID 路径字典序决定顺序。
- 候选不足 N 时不强行填满；不再用固定路径阈值 tau 控制入树或剪枝。

因为 e 在 [0,1] 内，孩子的 S 不大于父亲；配合“同分时祖先优先”，这个排序能够保持祖先闭包。

例如 N=2，四个候选都是根的直接孩子：

| 候选 | 原始分数 | c=1 时的分数 | c=0.6 时的分数 |
| --- | ---: | ---: | ---: |
| suffix A | 0.90 | 0.90 | 0.54 |
| suffix B | 0.80 | 0.80 | 0.48 |
| 模型 C | 0.60 | 0.60 | 0.60 |
| 模型 D | 0.50 | 0.50 | 0.50 |

开始保留 A、B；系数降到 0.6 后保留 C、A。节点上限仍然是 2，变化的是名额分配。

新候选先以轻量元数据参与选择，入选后再分配模型状态。满额时，新高分候选可以替换已有低分节点。淘汰父节点时其后代一起失效；以后重新提出相同路径，不能直接复用已失效的缓存。

## 5. 什么事件触发一次反馈

**触发条件：父节点 h 已经到达当前已确认前缀，而且它的全深度下一 token 预测可用。** 此时它的预测能够真正决定下一个输出 token。

仅仅在一个未确认分支上算完了全深度，不触发第一版控制器更新。一个节点先算完、后到达已确认前缀时，等到后者发生再反馈。

对每个尚未获得验证结果的父节点，保存一个后缀候选记录集合 R(h)。记录不是模型状态，不额外占 N，但有自己的 CPU 元数据与内存成本。

每条记录包含：

- 父节点的逻辑上下文标识，以及候选 token；不能只用会被复用的缓存槽编号。
- 第一次提出这条后缀边时的原始分数 q_i。
- 当时使用的系数 c_i，以及预测值 hat_p_i = min(1, c_i * q_i)。
- 这条记录是否已计入反馈。

同一父上下文、同一 token 的重复检索只保留第一条记录。即使后来边分数被模型读出替换，原来的后缀预测记录也不改变。对于检索提出但当前已经采用模型评分的孩子，也可以保存这一次后缀预测记录；它不覆盖模型边分数。

候选记录在 Top-N 筛选前生成，所以孩子被预算淘汰后，只要父节点后来得到有效验证，仍可评价它的后缀预测。这不要求为被淘汰孩子做额外模型前向：比较候选 token 与父节点的最终预测即可。

父路径已被确认不可能属于最终输出时，清理其反馈记录，不把它们标成失败。预算淘汰本身不是“父路径错误”的证据。待定记录在根前移时按前缀清理，请求结束时全部释放。

已经知道父节点最终预测之后再产生的候选，不回填成这个父节点的预测记录。每个父上下文最多反馈一次。

## 6. 每个父节点怎样小幅更新系数

设父节点 h 的全深度预测为：

\[
g_h=\arg\max_t p_T(t\mid h).
\]

对其记录集合中的每个候选 token t_i，定义：

\[
Y_i=\mathbf 1[t_i=g_h].
\]

也就是：命中为 1，没有命中为 0。这是对全深度预测的匹配，不需要外部标准答案。

这个父节点的反馈误差是：

\[
\delta_h=\frac{1}{|R(h)|}
\sum_{i\in R(h)}(Y_i-\hat p_i).
\]

这里比较的是**提议当时保存的调整后分数**，不是原始 q，也不是用最新系数重新算出的分数。父节点没有有效记录时跳过更新。

第一版使用对数系数的有界增量更新：

\[
\boxed{
u\leftarrow\operatorname{clip}
\left(u+\eta\delta_h,\log c_{\min},\log c_{\max}\right),
\qquad c\leftarrow\exp(u)
}
\]

其中 0 < c_min < 1 < c_max，eta > 0。持久状态保存的是裁剪后的 u，不额外积累一个越界的隐藏积分量。

- delta_h < 0：预测整体偏高，降低 c。
- delta_h > 0：预测整体偏低，提高 c。
- delta_h 接近 0：基本保持 c。

**不等待 32 条、64 条，也不等待多个父节点。** 一个父节点验证完，就用它已有的记录平均一次、更新一次。这里的平均只是汇总同一个父节点的孩子，不是额外攒一批数据。每个有记录的父节点贡献一次更新，不把它的多个互斥孩子当成独立验证事件。

举例：某父节点有两个后缀候选，当时预测值为 0.7 和 0.2；最终 token 是第一个，则：

\[
\delta_h=((1-0.7)+(0-0.2))/2=0.05.
\]

若两个候选都没有命中，则 delta_h = (0-0.7+0-0.2)/2 = -0.45，系数会向下调整。若为说明方便取 eta=0.1、更新前 c=1，则后一种情况得到 c=exp(-0.045)，约为 0.956；这个步长仅为算例，不是实测推荐值。

不要把 c 调整理解为自动找到了最优后缀占比。这里纠正的是已观察记录的平均预测偏差。

## 7. 更新与 Top-N 排序怎样衔接

反馈来了就更新系数，但一次排序过程中的系数必须固定。

1. 根据已经得到的全深度结果，处理当前已确认父节点的反馈。
2. 提交全深度决定的 token，删除不匹配分支，把接受的孩子设为新根；它不再占 N。
3. 如果正确路径上的下一节点也已算完，可以继续提交，并逐父节点反馈。不能先因新权重淘汰这个已知正确、可以立即接受的孩子。
4. 在下一次预算选择边界，固定当前 c，对所有仍采用 suffix 评分的边重新计算 e，再从新根重新计算 S。
5. 已有节点和本轮新候选使用同一个 c 竞争 N 个名额。选择完成后，再开始下一次模型推进。

旧候选不能一直使用旧系数，而新候选使用新系数。需要保存原始 q，避免在已经修正过的 e 上反复乘 c。

连续接受多个节点时，系数仍然每个父节点更新一次；路径重评分可以在这一段接受结束后统一执行，以减少重复遍历。每个请求的候选选择始终不超过 N；中间的提案元数据不等于已分配模型状态的节点。

被预算淘汰的候选记录只用于反馈，不会因系数变化自动恢复其失效模型状态。若候选以后再次被提出，则正常重新竞争名额。

## 8. 一次请求的完整流程

```text
初始化：c = 1，u = 0，建立本请求的候选记录；固定预算 N。

完成 prompt prefill，得到起始输出，建立已确认根。

循环，直到 EOS 或输出长度上限：
    1. 从当前根及允许扩展的候选上下文查询 suffix。
       对尚未验证的父上下文登记后缀预测，去重。
    2. 收集模型浅层/较深读出的候选；新读出替换已有边分数。
       新入选的模型候选也支持继续查询 suffix。
    3. 用本轮同一个 c 计算边分数和路径分数。
       在已有节点与新候选并集上保留最多 N 个，保持祖先闭包。
    4. 推进根以及保留节点中尚未算完的模型状态。
       到读出深度时返回第 2 步处理；每次模型调用前满足预算。
    5. 当已确认前缀上的父节点全深度预测可用：
       a. 用该父节点已有后缀记录计算误差，立即更新一次 c。
       b. 提交全深度 argmax，接受匹配孩子并前移根。
       c. 若匹配孩子不存在，仍提交这个 token，建立新的已确认根。
       d. 连续处理已经就绪的正确后续节点。
       e. 更新允许发布的 suffix 历史，清理失效记录，补充候选。
    6. 在下一次选择边界使用更新后的 c 重评分并执行预算选择。

请求结束：按原规则发布已完成输出，释放请求的树、记录和控制器状态。
```

生产者提出候选，消费者完成验证，反馈更新器调节一个标量；这是逻辑流水线，不要求额外启动独立 GPU 线程。反馈尚未到达时继续用现有 c。系数更新不引入额外模型前向，但日志、重评分、缓存管理及 CPU/GPU 通信都有成本，需要测量。

候选 token 可用作临时查询上下文，但未被接受前不能写入 suffix 历史；跨请求历史仍只发布已完成请求的输出。

## 9. 参数、边界与验证目标

第一版需要明确记录 N、eta、c_min、c_max、初始 c=1，以及“每请求重置、每父节点一次”的更新规则。模型读出深度、top-8、每次后缀查询的候选上限等设置沿用预算设计，并单独记录。

初始设计没有冻结 eta 或系数上下限。按本次“不增加校准集、统一实验设置”的要求，第 11 节提出事前指定的数值，不在 480 条评测数据上选优，也不额外要求开发集拟合。没有“反馈批大小”参数。N=64 沿用预算文档中的起点，不表示已经测得最优。

这个方案：

- 不训练分类器，不做梯度训练，不需要离线校准表或外部答案。
- 明确依赖推理过程中的验证反馈，属于在线自适应评分，也是一种轻量在线校准。
- 不属于 importance sampling，也不是完整 PID；第一版仅采用积分反馈思想。
- 不保证候选逐项校准、兄弟分数和为 1、路径乘积是真实接受概率，或吞吐一定提升。

只有一组系数只能纠正某种平均偏差；模型原始 softmax 仍未校准，不能据此宣称两种来源已经完全对齐。记录被预算淘汰的孩子能减少观测偏差，但未验证父路径仍缺少有效反馈。

实现后重点检查：每父节点只更新一次、旧预测快照不被覆盖、缓存槽复用不串记录、未确认分支不反馈、空记录跳过、系数有界且为正、模型覆盖后不再乘 suffix 系数、已有与新候选同轮同系数、N 计数与祖先闭包，以及正确路径的连续接受。

性能比较至少包含同 N 下的原始评分 c=1 与在线调整版本，报告正确路径覆盖、接受长度、无效推进行数、候选替换次数、系数轨迹、元数据开销和实际吞吐。N=0 时不保留草稿，也不为控制器额外生成后缀候选，直接使用无草稿回退。

最终输出始终由已确认前缀上的全深度预测决定。当前 Ouro BF16 的实际输出分歧仍待定位；算法提交规则不能替代有限精度实现的一致性检查。

## 11. 已实现接口与下一轮比较方案

### 实现与日志

- `BudgetConfig`、`budget_tree_decode`、`budget_tree_decode_steps` 位于 `loop_budget_decode.py`，无需传入 Calibration。单请求与 batch 使用同一状态机。
- `budget-raw`：模型 top-8 + suffix，固定 c=1；`budget-online`：同一候选生成、N 和选择规则，逐父节点更新 c；`budget-suffix`：同 N、c=1，只用 suffix 提案。
- 先选择 CPU 提案元数据，选中后才分配状态。N+1 个可回收槽即可运行任意输出长度；已确认链在回收前立即写入主 KV，因而三个预算臂均不使用旧 `flush_every` 延迟提交策略。
- 后缀记录用本请求完整生成路径作逻辑 key，与物理槽号分离。预算淘汰不删除待反馈记录，前缀确认后才清理不可能路径；完整结果已知后禁止补录。
- `--draft-node-budget` 控制 N；`--max-nodes` 仍是物理树缓冲区容量，预算臂要求至少 N+1。额外物理容量不会增加预算臂的活跃树规模。旧 WFD 为追加式槽管理，长输出不能把所有臂的物理容量简单设成 N+1。
- 逐题统计包括草稿峰值、预算淘汰/拒绝、替换数、正确路径覆盖、接受段长度、推进 rows、被丢弃且未接受节点的已执行 rows、查询/排序/反馈耗时和记录峰值。接受段长度包含最后的未命中 bonus token。
- `--trace-controller` 另记录逐父节点系数轨迹和 CPU 元数据字节估算，标记为诊断运行，不与正式吞吐混用。估算不包含 Python 分配器、完整树元数据及历史索引内存。原 ABSENT=0 近似保留；模型有限精度一致性仍需单独报告。

本地验证：`PYTHONPATH=src python -m pytest tests/test_loop_budget_decode.py -q` 为37项通过，包含 N=0/1、满额替换、快照去重、未确认父节点不反馈、连续接受、EOS、两个小模型骨干的 CPU/FP32 与 CUDA/BF16 缓存回收、serial/batch 对齐及无校准文件 CLI。全套回归中依赖真实 checkpoint/WFD 挂载的8项跳过；小模型结果不替代全尺寸一致性或速度评测。

### 本轮固定设置（用户确认更新）

两模型 × 六臂 × 九个 B × 一个题序 × 一次计时 = **108组，全部成功时51,840次计时请求生成**。OOM组保留错误而不填写吞吐，不自动扩展重复。`--check` 的串行 AR 参考和预热另计，不训练控制器。完整480题曾参与历史设计，不能称为未见盲测。

LoopSpec 原先被放在总计划 E02 的官方独立引擎对照里，没有接入本轮 CLI；这不能作为不比较双读出基线的理由。本轮新增 `loopspec-dual`，与其他臂共享 backbone、batch 执行器、精度和 attention。按官方 greedy 调度，d1 提出 top-1，d2 仅在预测不同时增加第二分支，两个分支保留到全深度验证；不用 suffix、top-N 排序或在线系数。Ouro 读出1/2，Huginn移植相同调度到4/8；后者不冒充官方 Raven checkpoint 结果。参考源码固定 `41aa710ed7c9ce908cffa03597be5d1df19d7b56`，已做逐轮调度对照。官方原生引擎 E02 仍单独登记。

旧 load192 短输出探测和 capacity-common 最大公共 batch 选择均已取消，旧记录仅留作历史。新矩阵每组使用完整480条、1024输出预算；禁用85%预估容量拦截，实际分配/预热/解码抛出的 CUDA OutOfMemoryError 才记为 OOM。每个模型/B/方法用独立子进程，退出后释放上下文；不推断其他 B 的结果，不缩减 B/N/长度。

旧固定批次结果保留在 `results/loopfill-batch480-20261104/`，不与continuous结果混合。串行AR参考的token解码器未变，验证源码后复用完整480条参考，迁移来源记录在新目录。continuous模式是有限队列的持续补位，prefill仍为逐请求整段执行；不是完整线上服务模拟。

8张 L20X 卡全部并行，统一 EXCLUSIVE_PROCESS、核心1980 MHz、显存应用频率3201 MHz、功率上限700 W。每卡固定4个CPU亲和性、Torch/OMP/MKL线程数1；同模型同B六臂固定同一UUID，跨B使用同型号同配置卡。每15秒记录实际频率、温度、显存和利用率。串行AR参考按请求分片并行补齐，在计时外合并为每模型480条；复用的旧参考及源码哈希迁移另存 provenance。

### 命令

八卡主实验由冻结的调度器启动；每个模型/B/方法使用独立子进程，统一传入 `--schedule continuous --allocation-guard disabled`。下面的prepare需要目标GPU空闲，现有运行不要重复启动：

```bash
python scripts/loop_batch_sweep.py prepare \
  --suite results/loopfill-batch480-20261104 \
  --out results/loopfill-continuous480-20261104 --schedule continuous
python results/loopfill-continuous480-20261104/source/scripts/loop_batch_sweep.py run \
  --out results/loopfill-continuous480-20261104
```

本轮只运行repeat-id=0；Huginn更换模型名、权重路径和输出目录。本轮自动运行入口为 `scripts/loop_batch_sweep.py`，冻结协议、源码快照和状态写入 `results/loopfill-continuous480-20261104/`；旧入口不再重启探测。不要传 `--calibration` 或 `--tau`。`--scoring raw` 是脚本保留的全局开关；`budget-online` 自身的 config/stats 明确记录 `scoring=online_suffix_i`，不会读取离线表。若只比较三个预算臂，物理容量可显式改为65；这种容量实验单独登记，不与上述共同缓冲区设置混合。
